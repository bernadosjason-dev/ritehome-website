# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The marketing site and lead-generation tooling for Ritehome Modular Systems, a modular cabinetry / interior fit-out company in Cagayan de Oro, Philippines. Live at `ritehomemodular.com` (see `CNAME`). Static HTML/CSS/JS — no framework, no build step, no `package.json` at the repo root.

Two parts, each deployed independently:
1. **The site itself** — static files, served as-is (GitHub Pages / Cloudflare).
2. **`cloudflare-worker/`** — "Hannah," the site's AI chat widget's backend, and also the backend for the site's two forms (`POST /lead`). Deployed with Wrangler, automatically from `main`.

## Commands

Preview the static site locally:
```
python3 -m http.server 8000
```
(`http://localhost:8000` and `http://127.0.0.1:8000` are already in the Worker's CORS allowlist for this reason.)

Deploying Hannah's backend after editing `cloudflare-worker/src/index.js` **is automatic**: `.github/workflows/deploy-hannah.yml` runs `wrangler deploy` on every push to `main` that touches `cloudflare-worker/`, authenticated with a `CLOUDFLARE_API_TOKEN` GitHub Actions secret. Merge to `main` and it ships — check the repo's **Actions** tab if it doesn't.

**Do not try to `wrangler deploy` from inside a Claude Code session.** This environment's own sandbox network policy blocks outbound connections to `api.cloudflare.com` (confirmed via `curl -sS "$HTTPS_PROXY/__agentproxy/status"` — a `connect_rejected` / 403 policy denial, not a token or auth problem). No token, secret, or wrangler config fixes that; the GitHub Actions workflow above is the only path that actually reaches Cloudflare. A `.claude/hooks/session-start.sh` SessionStart hook still installs `wrangler` locally each session for manual/local testing outside of `main`, but it cannot and should not be used to deploy from here.

There is no linter, formatter, or test suite in this repo — nothing to run beyond the above.

## Architecture

### `index.html` — one file, two modes
The homepage is a single ~2500-line file with no client-side router. It has two mutually exclusive display modes, toggled by JS at the bottom of the file (exposed as `window.RitehomeApp` so `assets/hannah.js` can call into it):
- **Stage mode** (default): a full-screen "slide deck" of `.slide` sections (portfolio shots, the design-team page, materials, the exploded module diagram, the four-systems overview, durability) navigated with `go(i)`.
- **Reading mode**: `.docsec` sections (process sequence, commercial terms/tiers, the inquiry form, FAQ, per-project detail pages, per-system photo galleries) revealed by `showDoc(id)` and dismissed by `showStage()`.

The five service pages (`kitchen-cabinets-cdo/`, `storage-wardrobes-cdo/`, `partitions-cdo/`, `workstations-cdo/`, `interior-design-cdo/`) are separate static pages that deep-link back into the homepage's reading-mode sections via `../index.html#<id>`.

`privacy-policy/` is a sixth static page (`schedule/`, documented further down, is a seventh), built on the same `assets/service-page.css` shell (plus its own `.legal`/`.legal-in` prose styles at the bottom of that file) but with no hero/sales sections — just a Privacy Policy and a short Terms of Use, in one page, linked from every other page's footer and the homepage menu. It exists because the site collects real personal data (the inquiry form, the site-visit request form, and anything a visitor gives Hannah) with nowhere on-site explaining that — a genuine Data Privacy Act (RA 10173) gap, and separately a hard requirement for running Google/Meta ads at all. Its content describes the *actual* data flows in this repo (the inquiry and site-visit forms → the Worker → Telegram + a Sheet via Google Forms, Hannah → whichever AI backend is active → Telegram → that same Sheet, bookings → Google Calendar, the Google Map/Fonts embeds) — if any of those change, this page goes stale and needs a matching edit, the same discipline as the tiers/pricing sync elsewhere in this file.

### The four systems × three tiers taxonomy
Everything Ritehome sells is framed as one of **Kitchen / Storage / Partition / Workspace**, each offered at one of three spec tiers — **Essential / Premium / Executive**. This exact language is duplicated in three places that must stay in sync: `index.html` (the tiers section), `assets/hannah.js`'s local KB, and `cloudflare-worker/src/index.js`'s `FACTS`. If tier names, systems, or their descriptions change on the site, update all three.

### Hannah (`assets/hannah.js` + `cloudflare-worker/`)
The chat widget works two ways depending on whether `HANNAH_ENDPOINT` (in `hannah.js`) is reachable:
- **No backend / backend unreachable**: `respondLocally()` keyword-matches against a hardcoded `KB` array — always available, never invents an answer, deliberately vague on pricing.
- **Backend reachable**: the Cloudflare Worker's `FACTS` + `RESPONSE_FORMAT` system prompt drives Gemini (default) → Claude → Cloudflare Workers AI, in that fallback order based on which API key secret is set. The model returns `{reply, needs_human, reason, chips, contact_info}`; `needs_human: true` pages Telegram (throttled to once per visitor session, via `already_escalated`). Hannah states a **2-business-hour response commitment** on escalation — that promise is only true because Telegram actually alerts someone in real time. The site's forms make the same promise only when the Worker reports Telegram really delivered (see the inquiry form section below); never make it anywhere Telegram isn't wired.
- **Contact capture on escalation**: the first "needs_human" Telegram alert has no way to reach the visitor back (Hannah's chat is anonymous) unless Hannah asks for a phone/email and the visitor gives one. That can land on a *later* message, after the main escalation ping already fired and throttled itself — so `contact_info` gets its own independent throttle (`already_contacted` client-side, `notifyTelegramContact` server-side) rather than reusing `alreadyEscalated`. `sanitizeContactInfo` requires a digit or `@` before forwarding anything, so the model can't turn this into noise.
- **Captured leads also land in the Sheet, not just Telegram**: when a visitor gives Hannah a phone/email, `logHannahLead` in `cloudflare-worker/src/index.js` submits it to the same Google Form the site's forms log through (`LEAD_FORM` — see the inquiry form section below), so it becomes a Sheet row, not only a Telegram message that scrolls away. Hannah never asks a visitor's name, so these rows carry a placeholder name, "Hannah lead (<contact>)". There's no dedupe/merge any more (that died with Apps Script) — a Google Form only appends rows.
- **Add-on/spec conversation**: `FACTS` also carries an `ADD-ON CATEGORIES` list per system (real accessory/feature names pulled from the internal estimator tools — never their costs). After a first ballpark, Hannah asks one optional, chip-offered follow-up about add-ons, and uses the answer only as a signal for which tier (Essential/Premium/Executive) to lean toward — never to compute or state a number for the add-on itself. This is the same total-only pricing boundary as everywhere else, just applied to accessories specifically.
- Output token budget is 700 across all three backends (raised from 400 after a real truncation bug — see `parseModelJSON`'s salvage logic, which exists specifically because even schema-enforced structured output can still get cut off mid-generation on a tight budget).
- **Chips**: short tap-able button labels the model can return alongside a reply (e.g. `["Kitchen","Storage","Partition","Workspace"]`) so a visitor can tap instead of type. Sanitized (count- and length-capped, rendered via `textContent` not `innerHTML`) on both the Worker and the widget, since the AI backend chooses the label text.
- **Pricing is a closely-scoped exception to "never invent a number"**: `FACTS` carries a small/medium/large × Essential/Premium/Executive `PRICING` table, in whole-system peso ranges only. Ritehome quotes per system as one total — Hannah is explicitly forbidden (in three separate places in the prompt, deliberately redundant) from ever giving a per-material, per-unit, or per-square/linear-metre price, even if asked directly or pressed to "just do the math."
- These ranges were derived from Ritehome's real internal per-project pricing-estimator tools (four private, unpublished HTML/JS apps — Kitchen, Closet & Cabinet, CR Partition, Office Tables & Partitions — not in this repo). Those tools' supplier costs, markup multipliers, and per-unit rates must never appear in this repo or in anything Hannah says; only final, banded totals may cross that boundary. If Ritehome's real rates move, the `PRICING` table has to be re-derived and hand-updated — nothing here recalculates it.
- **Kitchen Essential now interpolates between real per-length data points instead of matching one of three size bands — Kitchen Premium/Executive and every other system still use bands, and that split is deliberate, not an oversight**: a "Small — up to ~3.3m: ₱X" band was found to flatten a real, non-linear price curve into one number, understating anything short of the band's top end. Essential was corrected against seven real (length → price) points from the business (2.0m/2.5m/3.0m/3.3m/4.6m/5.0m/6.0m — see `FACTS`), and the prompt now tells the model to linearly interpolate between the two nearest points rather than pick a band. Premium and Executive don't have real per-length data yet, so they're still the old three-band guess — which can now occasionally sit at or below a nearby Essential figure once Essential moved to real numbers. `FACTS` explicitly tells the model to defer to the team rather than state a Premium/Executive figure that reads as cheaper than Essential for the same size. Storage is sized in metres the same way and likely has the identical banding problem — flagged for the same fix once real per-width data comes in, not yet done.
- **Kitchen sizing is numeric total-run-length math, not shape-name matching — two real bugs found this way**: (1) a customer describing an L-shape kitchen as "4 meters by 3 meters" got quoted off the 4m number alone, the 3m wall silently dropped; (2) once that was naively fixed to "just add the walls," a plain 4+3=7m sum is *also* wrong — real L-shape kitchens share a corner, so a straight sum over-counts it. `FACTS`'s `KITCHEN LAYOUT SHAPES` section now gives the actual formula per shape: Straight = the one wall; Galley/Parallel = sum of both runs (no shared corner); L-shape = WallA + WallB − 1.6m (one shared corner); U-shape = WallA + WallB + WallC − 3.2m (two corners); L-shape+island = the L-shape total plus the island's own run. A 4m + 3m L-shape is 5.4m, not 7m and not 4m — confirmed against Ritehome's real internal estimator output for that exact case. The `PRICING` table's Kitchen row was also de-shape-labeled (it used to read "Medium (~4.0m, L-shape)", which was itself steering the model to match "L-shape" straight to Medium regardless of actual size) — it's now pure numeric bands (Small ≤~3.3m / Medium ~3.3–4.6m / Large ~4.6m+), since the same shape name can land in any band depending on real measurements.
- **A measurement or count the customer already gave always outranks asking a size question or reciting a generic anchor size**: a customer who typed "2m width of kitchen cabinet" was getting Hannah's generic "~2.7m straight run" Small-tier blurb back — technically the right bracket, but ignoring the number they'd actually given, which reads as not having listened. `RESPONSE_FORMAT` now says explicitly: any wall/run length, wardrobe width, cubicle count, or seat count the customer states takes priority over asking about size at all — use it immediately and name it back in the reply ("for your 2m run...") instead of a generic size description. Chips for system/size/shape are still offered, but only when a real measurement wasn't already given.
- **Photo upload → vision-based estimate**: `hannah.js` has an attach button (paperclip icon, left of the text input) that lets a visitor upload a reference photo instead of, or alongside, typing measurements. The image is re-encoded to JPEG and downscaled to a 1280px long edge client-side (`compressImage`, canvas-based — this also sidesteps HEIC entirely, since canvas always outputs JPEG regardless of the source format) before it's sent, so a multi-MB phone photo never travels or costs API tokens at full size. The Worker forwards it as an inline image to whichever backend is active — Gemini via `inlineData`, Claude via an `image` content block — with `FACTS`'s new `IMAGE-BASED ESTIMATES` section instructing the model to judge scale off common reference objects (a standard door, base cabinet, fridge, tile) and run the same `KITCHEN LAYOUT SHAPES` math as a typed measurement, always caveating that it's a rough visual estimate, not a measured figure. The free Workers AI fallback has no vision-capable chat model, so it captions the photo first with `@cf/llava-hf/llava-1.5-7b-hf` and folds that description into the text turn — best-effort only, since this backend is the last resort anyway. A bad upload (wrong MIME type, oversized payload) is rejected before any AI call, in `extractImage`, to avoid paying for a vision call on garbage input.

### The site's forms (`index.html`'s `#inquiry` + `schedule/`'s site-visit request) → the Worker's `POST /lead`
Both forms POST JSON to `LEAD_ENDPOINT` (`https://ritehome-hannah.ritehome.workers.dev/lead` — set identically in both pages), handled by `handleLead` in `cloudflare-worker/src/index.js`, which deploys automatically like the rest of the Worker. It pages Telegram (the same `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` secrets Hannah uses) and, once `LEAD_FORM` is filled in, records the lead as a Sheet row by submitting it server-side to a plain Google Form linked to that Sheet (setup: `cloudflare-worker/README.md` step 5). Both are awaited, and the response is `{ok, telegram, sheet}` — `ok` (HTTP 200) only if at least one actually landed, otherwise HTTP 502. The pages act on that truthfully: success copy only on `ok`, the 2-business-hour promise only when `telegram` is true, and on any failure a pre-filled `mailto:` link plus phone/WhatsApp/Viber, so a lead is never silently swallowed. `/lead` rejects any `Origin` not in `ALLOWED_ORIGINS` (so it isn't a free Telegram relay), honours the `company` honeypot, caps field lengths, and requires a name plus a phone or email.
- **Why not Apps Script (removed — don't bring it back without a reason):** the forms used to post `no-cors` to a Google Apps Script web app. `no-cors` means the page can't see the response, so visitors always got "Thank you" whether anything saved or not — and the Apps Script Sheet turned out to have zero rows ever logged. The Apps Script editor also became unreachable from the owner's browser (a Google multi-account "can't open this file" failure), so it couldn't even be redeployed. The Worker path has neither problem: it deploys from `main` automatically and reports real delivery. Google Forms replaced Apps Script for the Sheet half precisely because it needs no script and no Google credentials, just a form the owner builds in the normal Forms UI.

### Scheduling (`schedule/index.html`)
A seventh static page, same `service-page.css` shell as the service pages plus the `.capacity-card`/`.formcard`/`.field` styles added for it at the bottom of that file. Two sections: a **Current Project Capacity** note (not a live calendar — deliberately) and a **site-visit request form** that posts through the exact same Worker `/lead` pipeline as the `#inquiry` form (with `source: "site-visit"` plus `address`, `visitDate`, `visitTime`), above which sits the booking modal described below.
- **The capacity note has no live data behind it, on purpose.** There's no project-management backend in this repo (an earlier internal project/expense tracker was deliberately moved to its own private repo, `bernadosjason-dev/ritehome-tracker` — see that history if it resurfaces as a request to "add the tracker back here"; it doesn't belong on the public marketing site, and neither does real client project data). Rather than fabricate "Project A: booked Oct 1–20"-style entries, this section states the real policy instead: 30–45 days from design finalisation + the 50% down payment, and tells the visitor to ask directly (via Hannah or the form) for the next real start date. If a genuine live-availability feed is ever wanted, it needs a real data source behind it first — don't backfill this section with invented dates to make it look more "live."
- **Why the form reuses the same `/lead` endpoint:** the 2-business-hour promise on this page is only honest because it's backed by the same Telegram pipeline as the main inquiry form, and the page only shows it after the Worker confirms Telegram delivered.
- Linked from the homepage menu (`<li><a href="schedule/index.html">Schedule</a></li>` — note this one's a real link, not a `data-doc` button like its sibling menu items, since it's a separate page, not a reading-mode section) and every other page's footer.
- **Booking modal (`assets/booking.js` + `assets/booking.css`) — real self-serve booking, in front of Google Calendar Appointment Schedules.** One "Book a call or site visit" button opens a popup with a Site visit / Call toggle on top and Google's own booking page (actual open slots on the team's calendar) in an iframe below. Google allows one appointment type and one duration per schedule, so the two types are two separate schedules, configured as the `BOOKING.visit.url` / `BOOKING.call.url` constants at the top of `booking.js`. Only `https://calendar.google.com/calendar/[u/N/]appointments/...` URLs are accepted — the embed src (Share → Website embed → Inline) or the booking page's address-bar URL; the `/u/N/` signed-in-account segment is stripped and `?gv=true` added. Short `calendar.app.google` links are rejected (they redirect to a page that won't frame). **Live config today: only `visit` is set** (Site visit schedule), so the toggle is hidden and the Schedule page's card reads "Book a free site visit" — when a Call schedule is added, set `BOOKING.call.url` *and* change that card's heading/text/button back to call-or-visit wording. If the Cloudflare CSP blocks `calendar.google.com` in `frame-src`, the browser's `securitypolicyviolation` event swaps the blank iframe for an "Open the booking calendar" new-tab link, so visitors never see an empty box. **It is completely inert until at least one URL is set**: `[data-book-section]` elements stay `hidden` and `[data-book]` links keep their plain `href` (`#request`, the request form), so the page never advertises instant booking that isn't wired up. With only one URL set, the toggle collapses to that one type. Google's iframe loads only when the modal is opened, not on page load. Bookings land in Google Calendar, *not* the Sheet and *not* Telegram; Google itself emails both sides. The request form below stays as the fallback ("No time that works? …request a different date" in the modal footer links to it). The modal's z-index sits just above Hannah's. The script and stylesheet are self-contained (`.bk-` prefix, own fallback tokens), so they can be dropped onto the homepage too, but right now they're only loaded on `schedule/`. Bump both `?v=` hashes when either file changes, same as Hannah's assets.
- **"Admin" for leads is the Google Sheet itself (plus Google Calendar for real bookings), not a page on this site.** This static site has no auth, so a custom admin webpage would mean either a fake client-side password (not real security) or a real backend that doesn't exist — not worth it when the Sheet's own account-level sharing already is a legitimate access boundary. Put a `Confirmed` column with a Pending/Confirmed/Declined dropdown at the end of whatever responses tab `LEAD_FORM` is linked to, for toggling a request's status by hand (rows for phone-in/walk-in bookings can be typed straight in). Keep it as the *last* column: Google Forms adds a column at the end of its responses range when the form gains a question, so a manual column must stay to the right of every form-owned column. (Two leftovers exist: the old Apps Script sheet, "Ritehome Website Inquiries" — tab "Untitled", `Confirmed` in column L, never received a row — and a separate, hand-run "Quotation Request Form" Google Form whose responses sheet has a `Confirmed` column at AC. Neither is wired to the site.)

### The CSP gotcha
`ritehomemodular.com`'s Cloudflare zone has its own Content-Security-Policy Transform Rule that is **not in this repo** (Rules → Transform Rules → Modify Response Header, in the Cloudflare dashboard). Its `connect-src` has to list any origin the browser needs to call — today that's only Hannah's worker, which also serves the forms' `/lead` (the Google Form submit happens server-side in the Worker, so `docs.google.com` does *not* need to be in `connect-src`). If a backend is reachable by `curl` but the live site silently never calls it (no console error, requests just don't fire), this is almost always why. See `cloudflare-worker/README.md`'s troubleshooting section.
The `#inquiry` section's embedded Google Map (`.mapcard iframe` in `index.html`) hits the same CSP, but on `frame-src`/`child-src` instead of `connect-src` — if that directive doesn't allow `https://www.google.com`, the map renders as a blank box with no console error, for the identical reason. The `schedule/` booking modal's iframe needs `https://calendar.google.com` in that same `frame-src`/`child-src` directive, or the modal opens to an empty panel.

### Hannah's position is set in TWO files, and `index.html` usually wins
`assets/hannah.css` styles `.hn-root` (position, size, the icon-only-on-mobile behavior), but `index.html` carries its own `body:not(.reading) .hn-root{bottom:calc(var(--pad) + 74px);}` — added to lift Hannah clear of the stage view's bottom thumbnail strip (`.indexbar`). That selector's specificity beats a bare `.hn-root` rule in `hannah.css` every time, on the site's *default* view (stage mode, not reading mode) — so a positioning fix that only touches `hannah.css` silently does nothing until the visitor switches to reading mode. If Hannah's position looks wrong specifically on the homepage's slide view, check `index.html` first, not `hannah.css`.

### Cache-bust the version query strings, every time
`hannah.css`/`hannah.js` are loaded as `assets/hannah.css?v=<hash>` / `assets/hannah.js?v=<hash>` in `index.html`, specifically so edits actually reach visitors instead of serving whatever Cloudflare's edge or the visitor's own browser already cached under the old URL. **Bump both `?v=` hashes in `index.html` in the same commit as any edit to either file.** A real debugging session got stuck on exactly this: CSS fixes kept "not working" on a live phone because the cache-bust hash was never touched, so nothing had actually reached the device being tested on.

### Standing product decisions worth not re-litigating
- The Facebook Messenger BOM-quotation-bot idea was deliberately dropped; Hannah (this repo's existing chat widget) is the one AI-bot surface for pricing conversations, not Messenger and not the separate (and last known to be broken) n8n "RiteHome Instant BOM from Tally Quote" workflow.
- Never surface a static price-lookup table or the internal estimator tools on the public site — pricing conversation happens through Hannah only, per the scoping above.
